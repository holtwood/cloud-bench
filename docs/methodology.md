# 评测方法论

> 本站每一个数字的来源、参数与口径。所有命令与参数公开，任何人都能据此复现。
>
> 脚本：`cloud-benchmark.sh`（8 阶段采集 + 汇总）。**参数以脚本为准**，本文档说明设计意图与读法。
>
> ⚠️ 该脚本**尚未随本仓库发布**（目前仍在作者私有仓库中）。本文档因此先行公开全部参数与口径，
> 可据此手工复现；脚本发布后会在此补上仓库内链接。

## 一、为什么不用现成方案

YABS、bench.sh、融合怪等主流脚本很快很好用，但它们的定位是「跑分」而非「评估能不能稳定跑业务」。
实测下来有几处盲区，恰恰决定了机器的实际体感：

| 盲区 | 后果 | 本站的补充 |
|---|---|---|
| 只有平均 IOPS，无长尾延迟 | 平均 26000 IOPS 看着漂亮，但 p99 可能是 952ms——数据库/容器的卡顿就是这么来的 | fio 记录 **p99 / p99.9** 延迟 |
| 几乎不做超售检测 | 邻居跑满时你的机器被抢 CPU，跑分那几分钟看不出来 | stress-ng 满载 20 分钟 + mpstat 持续记录 **%steal** |
| 只看标称核数 | 「2 核」可能是 1 物理核 × 2 超线程，「4 核」可能是 2 核 × 2 线程 | 从 `lscpu` 拆出 **物理核/线程**，并用多核扩展比交叉验证 |
| 不检测指令集 | 屏蔽 AVX 的机器跑不了某些工作负载，甚至直接 SIGILL | 检查 AVX/AVX-512 |
| 无原始数据 | 只有截图，无法复核、无法横向对比 | 原始产物全量保留 + 统一 schema 入库 |

**不是"更准"，而是"多测了几个维度"**——跑分同量级时，这些维度才决定体验。

## 二、测试环境与被测对象

### 被测机器

六台国内轻量/CVM 主机（2026-09 实测）。每台的元信息都记录在数据集里：

- **规格**：2C2G / 4C8G / 4C4G
- **物理核 vs 线程**：由 `lscpu` 的 `Thread(s) per core` × `Core(s) per socket` × `Socket(s)` 推导，
  并**只在结果满足「单核不高于多核」「扩展比合理」时才采信**（见第四节）
- **业务负载**：数据集 `role` 字段记录测试时跑了多少容器（生产机 vs 空机）——**这是重要的对比前提**
- **内核版本**：数据集 `kernel` 字段。版本差异实测可影响 9~23% 的成绩，跨机对比必须看这栏

### 测试时段

统一在**低峰期全核跑满**（脚本 `--at` 在远端定时，到点自动开跑，不受本地断网/关机影响）。
生产机在测试窗口内会被抢占资源，这一点已在 `role` 字段披露。

## 三、八个阶段

每阶段独立日志，失败不阻塞后续阶段（记入 `failed-stages.txt`）；重复执行会覆盖该阶段产物且不产生重复指标。
全部长任务在远端 `tmux` 中执行，SSH 断连不中断。

### 先看档位：为什么默认只要 16 分钟

实测全量耗时 **约 2 小时 28 分**，但分布极不均匀：

| 阶段 | 实测耗时 | 占比 |
|---|---|---|
| pts（含内核编译 87 分钟） | 1:49:20 | **74%** |
| stress | 20:03 | 13% |
| yabs | 7:40 | 5% |
| fio | 5:05 | 3% |
| deps / sysbench / env / net | < 6 分钟 | 4% |

**PTS 里最耗时的 `build-linux-kernel` 单项就占全量的 59%**，而轻量云用户不会在
2C2G 上编译内核。因此按档位裁剪：

| 档位 | 阶段 | 耗时 |
|---|---|---|
| `quick`（默认） | env, deps, fio, sysbench, stress(5m), net | ~16 分钟 |
| `standard` | quick + yabs + pts(7-Zip, redis) | ~40 分钟 |
| `full` | 全部八阶段（含内核编译） | ~2.5 小时 |

**关键：quick 档不损失任何差异化指标**——磁盘 p99（fio）、超售 %steal（stress）、
物理核识别（env）全在其中。被砍掉的是与 YABS 重叠的通用跑分。



### 1. `env` — 前置检查与系统信息

`lscpu` / `free` / `lsblk` / `os-release` / 虚拟化类型（DMI）→ `system-info.txt`。

**为什么单独成阶段**：后面所有对比都依赖这里读出来的物理核、内核、指令集。
另外 DMI 信息能区分**轻量应用服务器**（常见虚拟化标识）与 **CVM/ECS**。

### 2. `deps` — 工具安装

fio / sysbench / iperf3 / stress-ng / sysstat / PTS 所需的 php 扩展。

> 踩坑记录：apt 在部分镜像上会因交互式 debconf 提示而卡死数十分钟。脚本用
> `sudo env DEBIAN_FRONTEND=noninteractive` + `debconf-set-selections` + apt 超时兜底解决。

### 3. `yabs` — 快速跑分（交叉验证）

`yabs.sh -j -w yabs-result.json -g`（`-g` 跳过 Geekbench：需从海外 CDN 下载且常拿不到分数）。

**定位是交叉验证**：YABS 也测 fio 4K/64K，与第 5 阶段的精测互证。
数据集里保留为 `yabs_4k_total_iops`，与 `disk_4k_read_iops` 一起看——
两者差异过大说明测试条件或盘本身有异常。

### 4. `pts` — Phoronix Test Suite 固定 5 项

```
compress-7zip  openssl  build-linux-kernel  ramspeed  redis
```

- **7-Zip 压缩/解压**：综合 CPU 性能，跨架构可比性好
- **openssl sign/verify**：单线程加密性能，看 IPC 与指令集优化
- **build-linux-kernel**：最能代表"编译/构建类"真实负载（`defconfig`，非 `allmodconfig`——
  后者耗时数小时且是变体陷阱）
- **ramspeed**：内存带宽
- **redis SET（50 并发）**：应用层性能，同样本的最直观参考

> 踩坑记录：PTS 的 `batch-setup` 答案序列必须精确（第 7 问"跑全部变体"必须答 `n`，
> 否则会展开上千个变体组合）；后台执行必须用 `yes '1'` 喂 stdin，否则菜单会无限重印
> 把日志写到几十 GB。

### 5. `fio` — 磁盘精测（本方法论的核心）

| 项目 | 参数 |
|---|---|
| 4K 随机读 / 随机写 | `--bs=4k --iodepth=32 --numjobs=4 --direct=1 --rw=randread/randwrite --time_based --runtime=60` |
| 顺序读 / 写 | `--bs=1m --iodepth=16 --numjobs=4 --direct=1 --rw=read/write` |
| 延迟记录 | `--percentile_list=50:99:99.9` |
| 测试文件 | `numjobs=4` × `size`（`size` 随磁盘余量自适应，**见第五节口径说明**） |

`--direct=1` 绕过页缓存，测的是真实盘；`--time_based --runtime=60` 保证各机跑同样时长。
判定阈值：**p99 > 100ms 标红**（长尾严重，业务会明显卡顿），**> 20ms 标黄**。

### 6. `sysbench` — CPU 与内存

```bash
sysbench cpu --cpu-max-prime=20000 --threads=1    --time=60 run   # 单核
sysbench cpu --cpu-max-prime=20000 --threads=nproc --time=60 run  # 全核
sysbench memory --memory-block-size=1M --memory-total-size=100G --threads=1 --time=60 run
```

**单核成绩与全核成绩一起看**：两者之比（扩展比）能识破"超线程当核卖"——
4 线程只有单线程 2.09 倍，说明实际只有 2 个物理核，而不是 4 个。

### 7. `stress` — 超售检测

```bash
stress-ng --cpu $(nproc) --timeout 20m     # 满载 20 分钟
mpstat 1                                   # 每秒记录，取 %steal 均值与峰值
```

**%steal 是宿主机把 CPU 抢走的比例**——它才是最直接的超售证据：
跑分只是一瞬间，邻居跑满时你的机器还剩多少才是日常体验。
**实测结论：本次六台在满载压力下 %steal 均为 0.00**，说明这批轻量实例没有明显超售。

> ⚠️ 注意 `%steal` 为 0 是**有效结论**（没被超售），不是"没测"。数据集因此特意把它
> 排除在「零值即缺失」的判定之外。

### 8. `net` — 网络

Ookla Speedtest（就近节点）+ 跨机 iperf3 互测（`-P 8` 双向）。

> 轻量服务器的标称带宽（1M/4M）比测出来的峰值更值得看——它决定的是持续吞吐能力，
> 与瞬时测速不是一回事。

## 四、关键指标怎么读

| 指标 | 读法 |
|---|---|
| **4K 读 p99** | 决定"卡不卡"。均值再好，p99 952ms 意味着约 1% 的请求要等近 1 秒 |
| **%steal** | 决定"稳不稳"。0% 说明没被邻居抢；持续非 0 说明宿主机在超售 |
| **物理核 / 线程** | 看 `物理核` 列而非标称核数。`2核/2线程` 与 `1核/2线程` 是完全不同的东西 |
| **多核扩展比** | 全核 ÷ 单核。接近线程数说明真并行；远低于线程数说明共享物理核或有功耗墙 |
| **内核编译秒数** | 最能代表编译/构建类负载（npm install、docker build、源码编译） |
| **顺序读写** | 影响大文件传输与大块 IO；随机 4K 影响数据库与容器 |
| **AVX-512** | 影响科学计算、部分数据库与 AI 推理；缺失可能导致程序崩溃而非变慢 |

## 五、可比性约束（务必先读）

横向对比前必须核对以下几点，数据集里都有对应字段：

1. **内核版本不同**（`kernel` 字段）——实测 7.0 与 6.8 在同硬件上差 9~23%。
   这是最大的系统性偏差来源。
2. **fio 测试文件大小不同**（`numjobs` × `size`）——脚本按磁盘余量自适应：
   余量 < 20G → 1G×4，< 40G → 2G×4，否则 4G×4。
   六台实测中火山云是 1G×4（余量仅 8G）、腾讯云04 是 4G×4、其余为 2G×4。
   `--direct=1` 已排除页缓存影响，小文件仍可能少覆盖盘的物理区域，
   **横向对比 IOPS 时请把这一点记在心里**。测试文件大小记在 `fio_file_size_gb` 字段。
3. **业务负载不同**（`role` 字段）——生产机跑着 7~20 个容器，空机（如 04）成绩会更"干净"。
4. **测试时段**——不同时段的宿主机负载不同；本站统一取低峰期，但无法保证完全一致。
5. **单次采样**——每项测试跑一次（fio 内部为 60s 时基测试）。云盘性能存在波动，
   个位数百分比差异不必过度解读，量级差异才是结论。
6. **瞬时 vs 持续**——Speedtest 是瞬时带宽，轻量套餐的标称带宽才是持续能力的上限。

## 六、已知局限与数据缺口

- **子项失败会被如实标注**。阶段跑起来不等于每个子项都拿到结果——实测三例：
  火山云磁盘余量不足没跑内核编译、腾讯云03 内核编译跑了 29 分钟无结果、
  天翼云内存不足 redis-server 启动失败。数据集用 `metrics_missing` 字段列出这些缺口，
  网站上显示为灰色「—」，**不要读成"性能为 0"**。
- **不测流媒体解锁 / IP 质量**。这些与服务器性能无关，且本站面向国内机器。
- **不做"推荐榜"**。本站只提供数据，不接厂商、不给"最值得买"的结论。
- **物理核识别依赖 `lscpu` 的自报**。云厂商若在虚拟化层伪造拓扑，本站无法识破，
  但多核扩展比可以作为旁证（两者矛盾时以扩展比为准）。
